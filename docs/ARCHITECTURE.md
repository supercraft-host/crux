# Architecture

How the SDKs in this repo are organized, and why.

## Two layers

Every Crux SDK is structured as two layers:

1. **Transport layer** - HTTP, JSON, authentication headers, retries on
   429/503, error mapping. Wire-compatible with [`openapi/v1.yaml`](../openapi/v1.yaml).
2. **Ergonomic layer** - idiomatic types and methods for the host
   language (Promises in JS, `Task<T>` in C#, `await` in GDScript,
   `:Method()` chains in Lua).

The transport layer is the only thing that talks to Crux; the ergonomic
layer wraps it for the developer holding the keyboard. Keeping them
separate means a regression in one rarely breaks the other.

## OpenAPI-first

`openapi/v1.yaml` is the source of truth for the HTTP wire format. The
four first-party SDKs are *hand-written* against that spec, not
autogenerated. Trade-off:

| | Hand-written (what we ship) | Autogenerated |
|---|---|---|
| Boilerplate | low (we wrote it once) | low (generator did) |
| Idiomatic API | yes - `forPlayer`/`ForPlayer`/`init_player` naming per language | no - verbose, generator-ish |
| Type-checking integration | tight (TS strict, C# generics, Godot's typed dicts) | usually loose |
| Retry / backoff policy | shared, opinionated | absent |
| Bugfix latency | minutes | a generator-config trip |
| Surface evolution | costs N PRs (one per SDK) | costs 1 (regenerate) |

We chose hand-written for the four ecosystems where developer
ergonomics drives adoption (npm, Godot Asset Library, UPM, Wally). For
everything else - internal scripts, dashboards, analytics jobs in
Python, Rust microservices that proxy Crux - autogenerated clients are
the right move. The OpenAPI spec is sufficient to bootstrap them:

```bash
docker run --rm -v "${PWD}:/local" openapitools/openapi-generator-cli \
    generate -i /local/openapi/v1.yaml -g python -o /local/generated-python
```

Generators worth considering: `python`, `rust`, `go`, `csharp-netcore`,
`typescript-fetch`, `kotlin`, `swift5`, `dart`.

## Per-SDK conventions

### File layout

```
sdks/<name>/
├── README.md       quickstart + full API ref + troubleshooting + funnel
├── LICENSE         MIT
├── CHANGELOG.md    per-SDK semver history
├── <source>        the actual SDK
└── tests/          where the ecosystem supports headless tests
```

JS uses standard `src/` + `tests/` + `package.json`. Godot keeps the
`addons/crux/` shape Godot Asset Library expects. Unity keeps the UPM
package shape (`Packages/host.supercraft.crux/`). Roblox is one file
(`Crux.lua`) plus a `wally.toml` so Wally picks it up.

### Naming

Each language uses its native casing. The same method on every SDK:

| Concept | JS | Godot | Unity | Roblox |
|---|---|---|---|---|
| Anonymous login | `loginAnonymous()` | `login_anonymous()` | `LoginAnonymousAsync()` | `:VerifyPlayer()` |
| Submit a score | `submitScore(...)` | `submit_score(...)` | `SubmitScoreAsync(...)` | `:SubmitScore(...)` |
| Get top 10 | `getTop(id, 10)` | `get_top(id, 10)` | `GetTopAsync(id, 10)` | `:GetLeaderboardTop(id, 10)` |

We deliberately don't enforce identical names across SDKs. Native
casing reads better in each language; cross-SDK consistency at the
*method-name* level is a false god.

### Error handling

Every SDK maps HTTP errors to a single language-native exception type:

| SDK | Type |
|---|---|
| JS | `GSBError extends Error` (carries `statusCode`) |
| Godot | A `Dictionary` with `error` and `status` keys (GDScript convention) |
| Unity | `GSBException : Exception` (carries `StatusCode`) |
| Roblox | A `{ ok = false, status = N, message = "" }` table (Lua convention) |

`docs/ERROR_HANDLING.md` has the shared HTTP-status → semantics table.

### Auth

The same three auth modes work in every SDK:

- **API key** (player-side) - passed at init, identifies the project.
  Players still need to log in (anonymous or email) to get a JWT.
- **Server token** (server-side) - full project authority, never ship
  this to clients.
- **Player JWT** - obtained at login, attached to subsequent calls
  automatically by the SDK.

`docs/AUTH.md` has the diagrams.

## Why a monorepo

Pros: shared CI, shared docs, single MR for cross-cutting changes,
synchronized OpenAPI version, one repo to star.

Cons: less native discoverability per ecosystem (Godot Asset Library
prefers per-repo listings; Wally is okay with subdirectories; npm
doesn't care; UPM Git URL takes a `?path=` query string).

We mitigate the discoverability cost by:

- npm `package.json` is in `sdks/js/`, publishable as
  `crux-sdk` - npm doesn't care it's in a subfolder.
- Unity UPM uses the Git URL path query:
  `git+https://github.com/supercraft-host/crux.git?path=sdks/unity/Packages/host.supercraft.crux`.
- Godot Asset Library accepts a `subfolder` field on submission; we
  point at `sdks/godot/addons/crux/`.
- Wally takes a `path` in `wally.toml`; we point at `sdks/roblox/`.

If discoverability ever becomes a real problem, we'll split per-SDK
repos and turn this monorepo into a `git subtree` umbrella. So far it
hasn't.

## What's *not* here

- The Crux server itself (proprietary; hosted at
  [crux.supercraft.host](https://crux.supercraft.host/)).
- Admin tooling and dashboards.
- Per-tenant secrets and webhook signing keys.

If something in this repo looks like it shouldn't be public, please
open an issue immediately.
